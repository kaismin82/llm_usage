## Corrected spec

**Coding Plan quota, global:**
```http
GET https://api.z.ai/api/monitor/usage/quota/limit
Authorization: Bearer <Z.ai coding-plan API key>
Accept: application/json
```
**China:** replace host with `open.bigmodel.cn`. CodexBar adds no query for personal scope; its team scope adds `type=2` and `Bigmodel-Organization` / `Bigmodel-Project` headers. Do not assume those team conventions apply to personal subscriptions. No quota body is a real captured payload in this research; sample examples in clients are synthetic.

Check HTTP status and JSON `success === true`. Expected client-observed envelope is `{"code":200,"success":true,"data":{"level":"...","limits":[...]}}`; each limit includes `type`, integer `unit`, `number`, `percentage`, optional `usage`, `currentValue`, `remaining`, `usageDetails`, and `nextResetTime`. Interpret token windows via `type` (`TOKENS_LIMIT` or legacy `CREDIT_LIMIT`) plus unit/number: unit 3 with number 5 is five hours; unit 6 with number 1 is weekly. `nextResetTime` is epoch milliseconds, `percentage` is used percentage unless usable absolute fields let consumer recalculate. `TIME_LIMIT` unit 5/number 1 is rendered MCP/monthly by CodexBar. Do not promise missing weekly window exists for every plan.

**Reset-pack inventory (experimental, fixture-derived):**
```http
GET https://api.z.ai/api/biz/customer-package-reset/list?targetType=PERSONAL
Authorization: Bearer <same candidate key>
Accept: application/json
```
The sole reviewed consumer sends the same `ACTIVE_KEY` Bearer credential to both endpoints. Treat same-key success as likely, but unverified live. No POST/redeem path is evidenced. On `success:true`, compare prior successful `recordId` inventory; newly added ID or `available:false -> true` is a candidate grant. Display five-hour vs weekly scope and `expireTime`; do not label every available pack as newly granted.

Schema to parse cautiously (fields/sample are all a synthetic client fixture, not observed server payload):
```json
{"code":200,"success":true,"data":{"customerId":"41002358991004410","targetType":"PERSONAL","organizationId":null,"projectId":null,"lastFiveHourResetTime":"2026-09-11 06:02:16","lastWeekResetTime":null,"fiveHourResets":[{"recordId":910002,"expireTime":"2026-11-07 23:59:59","available":true}],"weekResets":[]}}
```
IDs are comparison keys; keep customerId as string to avoid JS precision loss. LogicIncZo parses date strings with `+08:00`, so interpret unoffset strings as UTC+08:00 provisionally, retain raw values. No authenticated JSON response has verified fields, timezone, or expiry semantics.
